# OpenShift AI on ocp-mgmt

OpenShift AI 3.5 provides the dashboard and KServe for single-GPU inference on `tr-gpu`. The operator uses `stable-3.5` with manual InstallPlan approval; the initial version is `3.5.1`. The `v2` DataScienceCluster enables dashboard, KServe, and AI Gateway with Models-as-a-Service. Training, pipelines, workbenches, model registry, and NIM remain disabled. The local model continues to use its single-replica KServe InferenceService.

[Models-as-a-Service routing](maas/README.md) exposes local Qwen and remote Claude through one authenticated gateway. This uses the external-model Technology Preview, including native Anthropic API passthrough, rather than migrating the existing GPU workload to an llm-d LLMInferenceService. Follow the staged rollout in that guide before enabling gateway clients.

The operator lives in `redhat-ods-operator`; it manages platform components in `redhat-ods-applications`. cert-manager, NFD, and the NVIDIA GPU Operator are installed separately. Model workloads belong in their own namespace.

The [dashboard](https://rhods-dashboard-redhat-ods-applications.apps.ocp-mgmt.rh-lab.morey.tech) uses OpenShift authentication. Hardware profile `tr-gpu-3090` selects `tr-gpu` and exactly one NVIDIA GPU, with defaults of 2 CPU and 8 GiB RAM. It must exist before admitting an InferenceService that references it.

## Rollout

```bash
kustomize build kubernetes/ocp-mgmt/system/redhat-ods-operator
oc get application redhat-ods-operator-system -n openshift-gitops
oc get subscription rhods-operator -n redhat-ods-operator
oc get installplan -n redhat-ods-operator
```

Inspect the pending InstallPlan's CSV names before approving it. Initial installation requires manual approval, just like an upgrade. After approval:

```bash
oc get csv -n redhat-ods-operator
oc get datasciencecluster default-dsc
oc get pods -n redhat-ods-applications
oc get routes -n redhat-ods-applications
```

GitOps manages the DataScienceCluster and hardware profile, not the Deployments and ConfigMaps generated by the operator. The DataScienceCluster uses `Prune=confirm` to guard platform removal. Enable model serving only after KServe's controller and webhooks are ready. Each InferenceService explicitly selects `Standard` (the current name for `RawDeployment`) and one replica.

## Model controller metrics

`odh-model-controller-monitor.yaml` adopts the existing `redhat-ods-applications/odh-model-controller-metrics-monitor` through server-side apply. The generated monitor references a bearer token file, which user-workload Prometheus prohibits, and an HTTPS Service port that does not exist. This causes `PrometheusOperatorRejectedResources` and leaves the model controller metrics unscraped.

The override selects the Service's named `http` port (8080), uses `/metrics` over HTTP, and removes the token-file and TLS settings. A read-only request from user-workload Prometheus verified HTTP 200 with Prometheus metrics and no credentials. This matches the controller's existing `--metrics-bind-address=:8080`; it does not change the controller or expose a new endpoint.

The annotation `opendatahub.io/managed: "false"` opts this resource out of the [OpenShift AI 3.5 deployment reconciler](https://github.com/red-hat-data-services/rhods-operator/blob/rhoai-3.5/pkg/controller/actions/deploy/action_deploy.go). On reconciliation, the operator removes its ownership reference and skips updating the monitor. GitOps owns its configuration; pruning/deletion is disabled. Recheck the Service port, authentication requirements, and opt-out behavior on upgrades. Removing the file alone retains the override; returning ownership to the operator requires a reviewed migration once its generated monitor is corrected.

After review, commit, human push, and Argo CD reconciliation, verify:

```bash
oc get servicemonitor odh-model-controller-metrics-monitor -n redhat-ods-applications -o yaml
oc logs deployment/prometheus-operator -n openshift-user-workload-monitoring -c prometheus-operator --since=10m
for pod in prometheus-user-workload-0 prometheus-user-workload-1; do
  oc -n openshift-user-workload-monitoring exec "$pod" -c prometheus -- \
    wget -qO- 'http://localhost:9090/api/v1/targets?state=active' |
    jq --arg pod "$pod" '{prometheus: $pod, targets: [.data.activeTargets[] | select(.scrapePool | contains("odh-model-controller-metrics-monitor")) | {scrapeUrl, health, lastError}]}'
done
```

Expect one healthy HTTP target on port 8080 per replica, no new rejection events for this monitor, and the `PrometheusOperatorRejectedResources` alert to clear after evaluation. Confirm the override remains synced after KServe reconciliation. These checks are deferred until GitOps deployment; server-side dry runs validate API acceptance but do not run Prometheus resource selection or scraping.
